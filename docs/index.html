A mini OS for ARM64 containers, in one binary under 100 kB.

PID 1, a small shell and the core utilities in one static Rust binary: no libc, no std, no crates. Init locks the container down before your command starts, and the kernel keeps it that way.

What is inside

This is the whole userland.

Every byte of /bin/kcontaineros, one pixel each. Apart from it the image holds symlinks, empty directories and four small files in /etc.

  • Static PIE. Loaded at a random address on every start; the binary relocates itself.
  • Read-only after start. No segment is both writable and executable, and the stack is not executable.
  • Pinned and reproducible. The compiler image is pinned by digest, and a rebuild from scratch gives the identical image layer.
  • No signal handlers, no threads. PID 1 consumes signals synchronously, so there is no handler code to race.

/sbin/init

PID 1. Locks the container down, starts your command, forwards every signal to it, reaps orphaned zombies and exits with your command's status. docker stop reaches a server at once, even one with no signal handling.

/bin/sh

A small shell, enough for Dockerfile RUN and CMD, simple entrypoint scripts and docker exec -it … sh. What it does not implement is a syntax error before the first command runs, never something else.

/bin/*

Core utilities with their common flags. An option a utility does not have is an error.

cat chmod chown cp echo env false kill ln ls mkdir mv ps pwd rm sleep touch true uname

src/sys.rs · the only way into the kernel
unsafe fn sc(n: usize, a: usize, b: usize, c: usize,
              d: usize, e: usize, f: usize) -> isize {
    let ret: isize;
    asm!(
        "svc 0",
        in("x8") n,
        inlateout("x0") a => ret,
        in("x1") b, in("x2") c, in("x3") d,
        in("x4") e, in("x5") f,
        options(nostack)
    );
    ret
}

The lockdown

Locked down before your command starts.

Code running inside, including code an attacker has taken over, cannot gain privilege, cannot loosen its restrictions and cannot run a program it brought with it. Init applies the restrictions to itself first; every process inherits them, and none can be undone from inside.

no_new_privsNo privilege gain
Setuid binaries and file capabilities grant nothing.
capability sets emptiedNo capabilities
Root in the container holds no privilege the kernel grants by capability, even under --privileged. What is left is what owning a file allows.
Landlock + filterRun or write, never both
Programs start only from the image's program directories, and nothing can be created, removed or written there. A binary dropped in /tmp or on a volume cannot be started, and memory files (memfd_create) cannot be created at all.
LandlockOnly the standard devices
null, zero, full, random, urandom, tty, console, the terminals and /dev/shm; also /dev/termination-log where Kubernetes mounts that file. Nothing else, whatever its permissions say: under --privileged that is every disk of the host. A device passed with --device has to be named in KCOS_DEV, each one by its own path.
LandlockRoot cannot write the kernel's files
Root still owns the files in /proc and /sys, but under init it cannot open them for writing: not /proc/sys, not the sysrq trigger. Reading them is not stopped.
seccomp filterReduced kernel surface
ptrace, process_vm_readv and process_vm_writev, new namespaces, mounts, chroot, kernel modules, bpf, io_uring, perf, keyrings, clock and hostname changes and AF_VSOCK sockets are refused. Calls newer than the filter knows are answered "not implemented".
read-only files, user nobodyNothing to tamper with
The image's files are read-only and owned by root, and the default user is nobody. It cannot modify the image.
not dumpablePID 1 is opaque
Other processes cannot read its memory or environment.
audited end to endNo escape found
A security audit of version 0.2.0 found no way out of the container and no way to gain privilege. It found three security claims that were false, fixed in 1.0.0. It was carried out by an AI model, not by an independent party. Read the audit summary →

For AI agents

A box for the tools an agent runs.

An agent that can run tools will sooner or later run something you did not intend. Text the model reads can steer it, so treat the tool process as something an attacker may end up directing. Here the usual next steps are refused by the kernel, not by instructions the model is asked to follow.

run or write, never bothFetch a program and run it
Nothing written at run time can be started as a program: not from /tmp, not from a volume, not from a memory file.
no capabilities, no_new_privsBecome root, or use root
There is nothing to escalate to. Root in the container holds no capability.
program directories are not writableReplace its own tools
Nothing running under init can modify or swap the tool server or anything beside it.
seccomp filterGo after the kernel
New namespaces, mounts, ptrace, bpf, io_uring and the other usual first steps of a container escape are refused.
the sealed imageUse what is lying around
There is no shell, no interpreter and no package manager in it: only init and what you copy in.
init forwards signalsKeep running after you say stop
docker stop reaches the tool server at once, and the short-lived processes agents leave behind are reaped.

A tool server in a sealed box

Build the tool server as a static binary and put it on the sealed image. The image cannot decide the network, memory, process count or what is mounted, so set those when you run it.

Dockerfile
FROM kcontaineros:sealed
COPY agent-tools /usr/local/bin/agent-tools
CMD ["agent-tools"]
Shell
docker run -i --rm --read-only --network none --ipc none \
    --memory 512m --pids-limit 128 \
    --tmpfs /work:uid=65534,gid=65534,mode=0700 \
    my-agent-tools

Run that way, a tool server can write its working files to /work and nowhere else, cannot start anything it writes there as a program, has no network, and holds no privilege. --ipc none matters for "nowhere else": without it Docker gives every container a writable /dev/shm of 64 MB.

What this does not contain

  • It does not limit the network. Without --network none or a network you restrict yourself, an agent can send anything it can read to anywhere it can reach.
  • It does not limit what can be read. Every file and secret you mount is readable by the tool server. Mount only what the tools need.
  • It does not judge what your tools do. A tool that deletes files will delete them for a hijacked agent too. The image contains the process, not the purpose.
  • It does not stop machine code loaded into the tool server itself. A hijacked process can map bytes as code inside its own memory. That code is still the tool server: same restrictions, no new program.
  • An interpreter is a way around the run rule. Copy in Python, Node or a shell and the agent can run any script through it. The rule stops programs brought in at run time, not code fed to an interpreter you shipped. The full image ships a small shell; the sealed image does not.
  • It is not a development environment. Agents that need compilers, package managers or dynamically linked tools do not fit. This is for a fixed set of tools built as static binaries.
  • It has not been tested with any agent framework.

Get started

Build it, then put your program on top.

The image builds inside Docker and always comes out as linux/arm64. Your program must be statically linked; a plain COPY needs no root.

Build and look around

make test runs the end-to-end tests against your local Docker daemon and needs an ARM64 host, bash, python3 and curl.

Shell
git clone https://github.com/BackendStack21/kcontaineros.git
cd kcontaineros
make build
docker run -it --rm kcontaineros

Put a binary on top

examples/hello-http in the repository is a complete image built this way, with a small Rust HTTP server.

Dockerfile
FROM kcontaineros
COPY my-server /usr/local/bin/my-server
CMD ["my-server"]

Or seal it

kcontaineros:sealed is init and nothing else: about 100 kB, no shell, no utilities, no writable directory. Use it as FROM when your image needs no RUN steps.

Shell
docker build --platform linux/arm64 \
    --target sealed -t kcontaineros:sealed .

Before you build on it

It runs as nobody, not root.
Build steps that write need USER 0 first; switch back with USER 65534:65534. Common questions shows how, and how to get a directory your program can write to.
Programs run only from /bin, /sbin and /usr.
Put yours in /usr/local/bin, or name its directory: ENV KCOS_EXEC=/app. Whatever directory holds programs cannot be written to at run time, together with the top-level directory it is in. Entries must be plain absolute paths to real directories: /, a trailing slash, . or .. components and anything reached through a symbolic link are ignored, with a warning. The top-level directory of an ignored entry is not writable all the same.
Only the standard devices can be used.
That is null, zero, full, random, urandom, tty, console, the terminals and /dev/shm. A device passed with --device has to be named: ENV KCOS_DEV=/dev/fuse. POSIX message queues (mq_open) do not work under init.
memfd_create is refused.
A few runtimes use it for JIT code or sealed memory; they need another base image.
Your command holds no capabilities.
That stays true whatever --cap-add or --privileged say. Ports below 1024 still work, because Docker makes them unprivileged.
New top-level directories cannot be created at run time.
Create them in the Dockerfile, or mount a volume there.
ENTRYPOINT is /sbin/init.
CMD runs under it. If you set your own ENTRYPOINT, or pass --entrypoint, init and everything it enforces are gone. Keep it with ENTRYPOINT ["/sbin/init", "--", "my-server"].
With --read-only, /tmp, /var/tmp and /run are read-only too.
Add --tmpfs /tmp if your program writes there.

Common questions

What people ask first.

Short answers for when you build on it.

How do I get a directory my program can write to?

Under init, a top-level directory is either for running programs or for writing, never both. /bin, /sbin, /usr and anything named in KCOS_EXEC hold programs and cannot be written to. Every other top-level directory that exists when the container starts can be, subject to ordinary file permissions. Since the image runs as nobody (65534), the directory also has to belong to that user. Out of the box only /tmp and /var/tmp qualify, plus the /dev/shm that Docker mounts in every container unless it is started with --ipc none.

A directory in the image. WORKDIR creates it owned by the current user, which is nobody:

Dockerfile
FROM kcontaineros
WORKDIR /data

Or create it as root and hand it over, for a path below an existing directory or when you do not want it to be the working directory:

Dockerfile
FROM kcontaineros
USER 0
RUN mkdir -p /var/lib/app && chown 65534:65534 /var/lib/app
USER 65534:65534

A volume. Mount it on a directory prepared as above and a new named volume takes over that directory's owner:

Shell
docker run -v app-data:/data my-image

Mounted on a path the image does not have, the volume is owned by root and nobody cannot write to it. Bind mounts keep the permissions they have on the host.

A temporary filesystem, owned by the user from the start:

Shell
docker run --tmpfs /scratch:uid=65534,gid=65534,mode=0700 my-image

With --read-only nothing in the image is writable, so every writable path has to be a volume or a tmpfs: docker run --read-only --tmpfs /tmp my-image.

What cannot be made writable:

  • anything under /bin, /sbin, /usr or the top-level directory of a KCOS_EXEC entry, even as a volume or tmpfs mounted there;
  • a directory inside a program directory, whatever links point at it: /data -> /usr/share/x is as read-only as /usr/share/x;
  • anything in /dev but the standard devices, /dev/shm and what KCOS_DEV names;
  • for root, /proc and /sys;
  • / itself: mkdir /new fails at run time, so create top-level directories in the Dockerfile or let a mount create them.

In the sealed image there is no /tmp. Mount one: --tmpfs /tmp:uid=65534,gid=65534,mode=0700.

My program fails with "permission denied" when it starts. Why?

Programs run only from /bin, /sbin and /usr. Copy yours to /usr/local/bin, or declare its directory in the Dockerfile:

Dockerfile
ENV KCOS_EXEC=/app

Several directories are separated by colons. Each must be a plain absolute path to a real directory, with no symbolic link on the way and no trailing slash: init prints a warning for an entry it cannot use. That directory's top-level directory then stops being writable, so a program in /app/bin cannot keep its data in /app/data. Nothing in /dev, /proc or /sys can be a program directory.

A program that is dynamically linked fails differently, with "no such file or directory" ("not found" from the shell): its loader is missing. Build it statically.

A RUN step in my Dockerfile fails with "permission denied".

The image's user is nobody and its directories are read-only. Switch to root for the build steps that write, then back:

Dockerfile
USER 0
RUN mkdir -p /etc/app && echo "mode=production" > /etc/app/config
USER 65534:65534

COPY and WORKDIR need no switch.

How do I use a device passed with --device?

Name it, in the Dockerfile or when starting the container:

Shell
docker run --device /dev/fuse -e KCOS_DEV=/dev/fuse my-image

Several devices are separated by colons. Without the name the device is there but cannot be opened. Ordinary permissions still apply on top, so a non-root user may need the device's group: --group-add.

Does my program need root? What about port 80?

No. Under init even root holds no capabilities, so running as root gains almost nothing, gives up the protection of the read-only image, and loses the ability to write anything in /proc and /sys. Ports below 1024 work for any user, because Docker makes them unprivileged inside a container. --cap-add and --privileged have no effect on the command.

A program that starts as root and switches user itself (some servers do) will fail to switch: start it as the final user instead.

How do I check that the lockdown is active?
Shell
docker run --rm my-image cat /proc/self/status

Look for NoNewPrivs: 1, Seccomp: 2 and CapEff: 0000000000000000. If the kernel has no Landlock, init prints a warning line when the container starts. make test checks the restrictions themselves.

How do I get a shell in a running container?

docker exec -it CONTAINER sh. That shell starts outside init: it cannot gain privileges and is under the system call filter, but it is not held to the run-or-write rule. The sealed image has no shell; use docker cp to get files out and docker logs to see output.

Can I use my existing entrypoint script?

Only if it stays within the shell's subset: commands, variables with ${NAME:-default}, pipes, && and ||, & and wait, redirections, cd, export, umask, set --, exec. A script with if, loops, $(…), [, globs, trap, read, . or ${NAME:?} stops with a syntax error before its first command runs. Either put the logic in your program, or call the program directly:

Dockerfile
ENTRYPOINT ["/sbin/init", "--", "my-server", "--config", "/etc/app/config"]

Keep /sbin/init first whenever you set ENTRYPOINT; without it nothing on this page is enforced.

How do I add CA certificates or timezone data?

Copy them from an image that has them:

Dockerfile
FROM alpine AS certs
RUN apk add --no-cache ca-certificates tzdata

FROM kcontaineros
COPY --from=certs /etc/ssl/certs/ca-certificates.crt /etc/ssl/certs/
COPY --from=certs /usr/share/zoneinfo /usr/share/zoneinfo
My runtime fails on memfd_create, ptrace or io_uring.

Those calls are refused on purpose and there is no switch to allow them. A program that needs them needs another base image.

Does it work on Kubernetes, or with user namespaces?

Neither has been tested. Nothing in the image depends on Docker itself, but that is reasoning, not a result.

Limits

What it will not do, said as plainly as what it does.

A small image leaves things out on purpose, and no lockdown is a guarantee. Read this before you rely on it.

Static binaries only.
There is no libc and no dynamic loader. Rust on musl and busybox are tested. Go with CGO_ENABLED=0 and Zig produce the same kind of binary but are not in the test suite. A dynamically linked program needs its loader and libraries copied in.
ARM64 only.
linux/arm64 is the only supported architecture. docker build stops with an error for any other.
No CA certificates, timezone data or /etc/services.
Copy them in if your program makes TLS connections or needs local time.
The shell is not POSIX-complete.
It has no if, for, while or case, no functions, no globbing, no $(…), no here-documents, no trap or read, and no [. Scripts that use them stop with a syntax error before doing anything. There is no test command either. Copy in another shell if a script needs more.
One command, no supervisor.
Init runs a single command and does not restart it. Use the shell's & and wait for more than one process.
No package manager and no adduser.
Add files with COPY. /etc/passwd has root and nobody.
A userland, not a bootable OS.
The kernel comes from the container runtime. kContainerOS does not boot on bare metal or in a VM.

What the lockdown does not guarantee

No image can honestly claim these, and this one does not.

  • It is not a guarantee against kernel bugs. The filter removes the interfaces most exploits start from; it cannot remove the kernel.
  • Code that is already running can still compute. An attacker with code execution inside your server can use what your server can reach: its files, its network, its memory. The restrictions stop them going further, not from being there.
  • "Cannot run" means "cannot be started as a program". A process can still map bytes into its own memory as executable code and jump to them; neither Landlock nor the filter prevents that, because every dynamic loader and JIT does the same. Such code runs inside the process it was loaded into, under every restriction above, and cannot become a new program. Mount writable directories noexec (Docker's --tmpfs does by default) to stop files there being mapped as code.
  • Processes of the same user can read and write each other's memory through /proc/PID/mem, read-only pages included, unless the host enables Yama: the filter refuses the system calls made for it, not the file. Root can read there, not write. Run one service per container.
  • docker exec, --entrypoint and RUN steps start outside init. A shell or utility started that way still applies no_new_privs and the filter to itself, but keeps the capabilities Docker gave it and is not under the Landlock rules: build steps have to be able to write the image. Other programs started that way get only what Docker gives them.
  • On kernels without Landlock (before 5.19, or with it disabled) init prints a warning and the run-or-write rule is not enforced. Everything else is; if the filter itself cannot be installed, or Landlock is there and its rules cannot be set up, init refuses to start. As PID 1 it applies all of it whatever an outer filter answers.
12 more limits of the lockdown
  • As root, a program cannot write to /proc or /sys at all, its own /proc/self/oom_score_adj included. Run as a non-root user, the default, and ordinary file permissions apply there instead.
  • Root can still read what root owns in /proc and /sys. In a --privileged container, where Docker hides nothing, that includes kernel state such as /proc/slabinfo, /proc/vmallocinfo and the names of other containers' keyrings in /proc/keys. What needs a capability to read (/proc/kcore, /proc/kmsg, kernel addresses) stays hidden. The default user reads none of it.
  • A device that is not named can still be opened for neither reading nor writing (access mode 3). Nothing can be read from it, written to it or, on Linux 6.10 and later, asked of it with ioctl. On older kernels Landlock cannot stop the ioctl: do not pass a device there that you have not named.
  • A device in a directory of its own (/dev/net/tun) switches the confinement of reads on, as an unnamed device does (see the Docker Desktop note below): what else is in that directory was not named.
  • The rules go by where things are mounted when init starts. They assume the usual layout, and a container started otherwise gets less: a device node outside /dev (mapped there with --device /dev/x:/data/x, or on a volume mounted without nodev) is an ordinary file; a /proc or /sys mounted somewhere else is an ordinary directory; and one volume mounted both inside a program directory and somewhere writable can be written through the second path and run through the first. Mount a volume in one place.
  • Whoever owns a file can still change its permissions, timestamps and extended attributes (user.*), in program directories too: root for the image's files, the default user for files an image built on top copied in with --chown. Nobody can change what is in them.
  • A dynamic loader you ship is a program that loads programs. Copy in ld-musl or ld-linux and it will map and run a binary from any directory not mounted noexec, as it does with every shared library.
  • Host directories shared by Docker Desktop (a bind mount from macOS or Windows) can be read but not written to, and programs in them cannot be started: their filesystem cannot be matched by any Landlock rule. When /dev holds anything beyond the standard entries and what KCOS_DEV names (--privileged, an unnamed --device, a mount under /dev), they cannot be read either. Use a volume. Bind mounts on a Linux host are not affected.
  • The shell will interpret a script from anywhere, including one an attacker wrote to /tmp. It cannot be executed directly, and the shell running it is under the same restrictions, but it is attacker-chosen logic. The sealed image has no shell.
  • Started as non-root, or as root without CAP_SETPCAP, init cannot empty the capability bounding set. It does not matter: with no_new_privs nothing can draw on it.
  • No stack protector or branch protection (BTI/PAC). Both need a nightly compiler for this target. For the same reason the unwind tables of the prebuilt core library are still in the binary, unused; the picture of the binary shows them.
  • User-namespace remapping has not been tested.
